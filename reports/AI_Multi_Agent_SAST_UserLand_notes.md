# AI 기반 Multi-Agent SAST 발표 대본

발표 분량은 약 6~8분을 기준으로 작성했습니다. 슬라이드의 보안 결과는 모두 **검토 결과** 또는 **코드상 가능성**이며, 실제 공격 성공을 뜻하지 않습니다.

## 1장. 표지

“안녕하세요. 저는 Raspberry Pi UserLand라는 대규모 C/C++ 저장소를 대상으로, AI가 맡을 수 있는 역할을 여섯 단계로 나눈 SAST 워크플로를 만들었습니다. 핵심은 위험 함수만 찾는 것이 아니라, 후보의 문맥을 모으고 근거를 다시 검증해 사람이 판단하기 쉬운 보고서로 만드는 것입니다.”

발표 포인트: 654개 파일, 235,816줄, 6개 역할.

## 2장. 과제 목표와 문제

“전체 저장소에는 C/C++ 코드가 23만 줄 이상 있습니다. 처음 스캔하면 583개의 검토 후보가 나옵니다. 하지만 `strcpy`나 `malloc`이 보인다는 이유만으로 취약점이라고 할 수 없습니다. 그래서 후보를 우선순위화하고, 실제 입력 경로와 안전장치를 확인한 뒤 가능성 높음·낮음·정보 부족으로 구분하는 것을 목표로 했습니다.”

강조 문장: “위험 함수는 출발점이지, 취약점 확정이 아닙니다.”

## 3장. 전체 아키텍처

“Scanner는 후보를 찾고, Context는 후보가 속한 함수와 호출 관계를 모읍니다. Triage는 중복을 합치고 우선순위를 정합니다. Security Review는 입력 경로와 버퍼 크기, 길이 검사를 분석합니다. Verification은 인용한 파일과 줄번호가 실제 코드와 같은지, 결론이 과장되지 않았는지 다시 확인합니다. 마지막 Report Agent가 JSON, Markdown, HTML 결과를 만듭니다.”

“외부 LLM API는 연결하지 않았습니다. 프롬프트와 응답 스키마를 기록했고, 사람이 작성한 검토 결과는 `human_provided_review`로 명시했습니다.”

## 4장. Batch 분할과 실제 결과

“파일 경로를 정렬한 뒤 코드 줄 수가 비슷하도록 세 배치로 나눴습니다. 각 배치는 약 7만 8천 줄입니다. 파일 수는 209, 177, 268개이고 후보는 378, 101, 104개였습니다. 세 배치의 후보 합계 583개는 전체 스캔 결과와 후보 ID까지 일치했고 오류는 없었습니다.”

“첫 번째 배치에 후보가 많은 것은 분할 실패가 아니라, 위험 함수가 많이 쓰인 코드 영역이 그 배치에 몰려 있기 때문입니다.”

## 5장. 토큰 절약 전략

“저장소 전체를 AI에 한 번에 전달하지 않습니다. 위험도가 높은 후보부터 보고, 후보 함수는 140줄, 분석 묶음은 최대 220줄로 제한했습니다. 호출자 코드는 두 개, 피호출자 코드는 세 개를 우선하며, 같은 원인의 후보는 통합합니다. 그래도 판단이 부족할 때만 관련 함수나 매크로를 추가로 수집합니다.”

“중요한 점은 내용을 무조건 자르는 것이 아니라, 부족하면 추가 수집하고 끝까지 알 수 없으면 정보 부족으로 남기는 것입니다.”

## 6장. AN-010 분석 사례

“AN-010에서는 명령행의 등호 뒤 값이 `param_val`로 추출되고, `dtoverlay_apply_override` 경로를 거쳐 `strcpy`의 원본 인자로 전달되는 코드 경로가 확인됐습니다. 목적지는 `dtoverlay.c` 1852줄의 256바이트 고정 배열이고, 1859줄에서 길이 제한 없는 복사가 수행됩니다.”

“복사 전에 255자 제한 검사는 확인되지 않아 검토 결과는 취약 가능성 높음, 신뢰도 97로 기록했습니다. 하지만 동적 재현, 실제 공격 성공, 실행 권한과 배포 조건은 확인하지 않았습니다. 따라서 이것은 확정 취약점이 아니라 코드상 가능성입니다.”

## 7장. 차별점과 신뢰성 장치

“단순 grep은 함수 이름을 발견하면 끝납니다. 이 도구는 후보에서 문맥을 모으고, 중복을 합치고, 근거와 반대 근거를 분석하고, 다시 검증해 보고서로 연결합니다. 분석 10건에서 인용 62개를 실제 원본과 대조했습니다. 최종 분류는 가능성 낮음 8건, 정보 부족 1건, 가능성 높음 1건입니다.”

“또한 사람이 제공한 검토 데이터를 자동 AI 분석처럼 표시하지 않아 결과의 출처를 분명히 했습니다.”

## 8장. 한계·향후 개선·결론

“현재 호출 관계는 정규식 기반이므로 매크로와 함수 포인터, 복잡한 전처리 조건을 완전히 해석하지 못합니다. 다음 단계는 AN-010을 안전한 최소 테스트로 재현하고 ASan과 UBSan 증거를 수집하는 것입니다. 정보가 부족한 AN-007은 libfdt의 문자열 종료와 DTB 검증 경로를 더 조사해야 합니다.”

마무리 문장: “찾는 속도는 AI로 높이고, 믿을 수 있는 결론은 코드 근거와 독립 검증으로 만든 것이 이 프로젝트의 핵심입니다.”

## 발표 자료의 근거 파일

- `reports/batch_results.json`: 저장소·배치별 파일 수, 코드 줄 수, 후보 수, 실행 시간, 오류 수
- `reports/analysis_results.json`: 10개 분석 사례, 판정 집계, 검증 인용 수, AN-010/AN-007 결과
- `reports/context_bundles.json`: 함수 문맥 및 코드량 제한
- `reports/architecture.md`: 에이전트 책임과 입출력 흐름
- `reports/token_strategy.md`: 토큰 절약 전략과 도입 이유
- `reports/differentiation_report.md`: 단순 grep 방식과의 비교 및 한계
- `reports/validation_report.md`: 결과 정합성 검증
